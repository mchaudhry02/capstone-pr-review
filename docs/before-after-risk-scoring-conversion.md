# Before/After Evidence: Risk-Scoring Deterministic Conversion

## What changed

**Before:** `skills/risk-scoring.md` described the severity->recommendation
mapping rules, but as a "skill" the reviewer agent would apply via LLM
reasoning on every call — an LLM call re-deriving a fixed lookup table
every single time.

**After:** `skills/risk_scoring.py` — the same rules as pure Python code.
The reviewer agent generates `findings` (the actual judgment-heavy part),
then calls this deterministic function to get `overall_risk_score` and
`overall_recommendation` instead of reasoning it out itself.

## Latency

| | Before (LLM reasoning) | After (deterministic code) |
|---|---|---|
| Measurement basis | **Estimated**, not directly measured — no live reviewer agent exists yet to time (see `docs/gap-inventory.md`'s "Known Remaining Gap"). Typical LLM API call latency for a small reasoning step is commonly in the several-hundred-ms to low-seconds range. | **Measured directly**: 10,000 calls to `score()` averaged **0.0011 ms/call** (see raw run below) |
| Honest caveat | This column is an industry-typical estimate, not this project's own measurement. Flagged as such rather than presented as measured fact. | This column is real, reproducible — run `python3 skills/risk_scoring.py` to verify |

```
10,000 calls in 0.0110s -> 0.0011 ms/call average
```

Even granting substantial uncertainty on the "before" side, the
difference is several orders of magnitude — this is not a close call.

## Cost

| | Before | After |
|---|---|---|
| Marginal cost per call | Non-zero — an LLM API call, however small the prompt, consumes billable tokens | **$0** — pure local computation, no API call |
| At scale (e.g. 10,000 PR reviews) | Would accumulate real cost purely for re-deriving a fixed lookup table each time | Free, regardless of volume |

## Predictability

| | Before | After |
|---|---|---|
| Same input, same output? | Not guaranteed — LLM outputs can vary run to run even with identical input (temperature, model updates) | **Guaranteed** — pure function, same input always produces same output. Verified by the 9-case self-test covering every rule branch. |
| Directly relevant baseline finding | `docs/baseline-metrics.md` found the *human* baseline scored inconsistently on Risk Flagging (1/2 across all seeded-bug PRs) — the original motivation for building `risk-scoring.md` at all. An LLM applying the same rules via reasoning risks reintroducing that inconsistency; deterministic code cannot. | |

## Maintainability

| | Before | After |
|---|---|---|
| How do you change a rule? | Edit prose in `skills/risk-scoring.md` and hope the agent's reasoning still reliably follows it | Edit the `score()` function; the 9-case self-test immediately shows if the change broke any existing rule branch |
| How do you verify correctness? | Would require running many LLM calls across various finding combinations and manually checking outputs | `python3 skills/risk_scoring.py` — deterministic, instant, CI-enforceable |

## Audit Clarity

| | Before | After |
|---|---|---|
| Can you explain why a specific recommendation was made? | Only by inspecting the LLM's own stated reasoning in that specific response — not independently re-derivable | The `reasoning` field is generated by the same fixed logic every time; any reviewer can re-run `score()` on the same findings and get an identical, explainable result |
| CI-testable? | Not practically — would require live LLM calls in CI, which is slow, costs money, and is non-deterministic | **Yes** — `skills/risk_scoring.py`'s self-test can run in CI as a pure unit test (no API calls, no cost, no flakiness) |

## Consequences of This Conversion

- **Positive:** faster, free, deterministic, directly CI-testable, and
  structurally cannot reintroduce the baseline's Risk Flagging
  inconsistency
- **Trade-off:** the rules are now fixed in code, not something the agent
  can flexibly reinterpret for an edge case the rules didn't anticipate.
  If a genuinely novel finding pattern doesn't fit the existing severity
  categories cleanly, deterministic code will apply the rule mechanically
  rather than exercising judgment. This is treated as an acceptable
  trade-off since the rules were already meant to be applied mechanically
  — see the ADR for the full reasoning and rejected alternatives.

## Status
Conversion complete and self-tested (9/9 rule-branch cases pass). Full
decision reasoning in `docs/adr/ADR-001-deterministic-risk-scoring.md`.
